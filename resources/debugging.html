Debugging Techniques

Segfaults, bus errors, memory leaks — every Pisciner faces them. Here are the essential tools and strategies for debugging C programs effectively.

Using GDB

GDB (GNU Debugger) lets you step through your program, inspect variables, and find exactly where a crash occurs.

# Compile with debug symbols
gcc -Wall -Wextra -Werror -g -o program file.c

# Start GDB
gdb ./program

# Common GDB commands inside the debugger:
run              # Run the program
break main       # Set breakpoint at main
break file.c:42  # Set breakpoint at line 42
step             # Step into function call
next             # Step over function call
print x          # Print value of variable x
backtrace        # Show call stack
continue         # Continue execution
quit             # Exit GDB

Tip: When a segfault occurs, run bt (backtrace) in GDB to see the exact function call chain that led to the crash.

Using Valgrind

Valgrind detects memory leaks, invalid reads/writes, and use-after-free errors.

# Basic memory check
valgrind ./program

# Full leak detection
valgrind --leak-check=full ./program

# Show details of every leak
valgrind --leak-check=full --show-leak-kinds=all ./program

# Track origins of uninitialized values
valgrind --track-origins=yes ./program

Valgrind output shows each leak with a stack trace. Look for definitely lost blocks — those are leaks you must fix.

Using Address Sanitizer

Address Sanitizer is a fast memory error detector built into GCC. It catches buffer overflows, use-after-free, and more.

gcc -Wall -Wextra -Werror -g -fsanitize=address -o program file.c
./program

When an error is detected, the program prints a detailed report showing the type of error, the memory address, and a stack trace.

Common Debugging Patterns

IssueLikely CauseHow to Debug
SegfaultNULL pointer dereference, buffer overflow, stack overflowRun in GDB, get backtrace
Bus errorMisaligned memory access, accessing unmapped memoryCheck pointer alignment, verify mmap usage
Double freeCalling free() twice on same pointerRun Valgrind, trace free calls
Buffer overflowWriting beyond allocated memoryUse Address Sanitizer
Memory leakAllocated memory never freedRun Valgrind --leak-check=full
Use-after-freeAccessing memory after freeing itAddress Sanitizer or Valgrind

Printf Debugging

When you cannot use GDB or Valgrind, strategic printf (or ft_putstr/ft_putnbr) statements can isolate issues:

// Print variable values at key points
ft_putstr("Entering loop, i = ");
ft_putnbr(i);
ft_putchar('\n');

// Print before and after a suspicious operation
ft_putstr("Before malloc\n");
ptr = malloc(size);
ft_putstr("After malloc\n");

// Confirm function entry/exit
ft_putstr("ft_strdup called with: ");
ft_putstr(src);
ft_putchar('\n');

Remember: Remove all debug printf/ft_putstr calls before submission. They violate the Norm if left in.

Debugging with assert

Use assert from <assert.h> to validate assumptions during development:

#include <assert.h>

int     ft_strlen(char *str)
{
    int len;

    assert(str != NULL);  // Crash if str is NULL
    len = 0;
    while (str[len])
        len++;
    return (len);
}

Assertions are disabled when compiling with -DNDEBUG, so they do not affect the final submission binary.
