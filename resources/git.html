Git Guide for the Piscine

Git is how you submit all your projects during the Piscine. Every module, exam, and rush is delivered via a Git push to a designated repository.

Overview

During the Piscine, you will be assigned a personal Git repository on the school's platform. You clone it, work locally, commit your changes, and push them to submit. The evaluation system picks up your pushed code automatically. Understanding the basic Git workflow is essential from day one.

Basic Commands

CommandDescriptionExample
git initInitialize a new repositorygit init my_project
git cloneCopy a remote repository locallygit clone <repo-url>
git addStage files for commitgit add file.c or git add .
git commitCommit staged changesgit commit -m "message"
git pushPush commits to remotegit push origin main
git statusShow working tree statusgit status
git logShow commit historygit log --oneline
git pullFetch and merge changesgit pull origin main
git diffShow unstaged changesgit diff

Typical Workflow

# Start the day — pull latest changes
git pull origin main

# Work on your files...

# Check what changed
git status

# Stage your changes
git add ex00/ft_putchar.c ex01/*.c

# Commit with a clear message
git commit -m "Complete ex00 and ex01 for C00"

# Submit your work
git push origin main

.gitignore for C Projects

A proper .gitignore prevents compiled binaries and temporary files from being committed. Create this file in your repository root:

# Object files
*.o
*.obj

# Executables
*.out
*.exe
a.out

# Editor temp files
*.swp
*.swo
*~

# OS files
.DS_Store
Thumbs.db

# Debug files
*.dSYM/

How Submission Works

Submission is simply a git push. The evaluation system checks the remote repository for your latest commit at the submission deadline. There is no upload form or separate submission tool — your push is the submission.

Critical: Pushing after the deadline will mark your work as late or not counted. Always push well before the cutoff time.

Common Mistakes

  • Forgetting .gitignore — committing .o files and binaries bloats the repository
  • Committing compiled binaries — always check before adding; use git status to review
  • Large commits — commit frequently with focused messages, not once at the end
  • Pushing without pulling first — leads to conflicts and rejected pushes
  • Force pushing — git push --force can destroy teammates' work and lose history
  • Wrong branch — ensure you are on the correct branch before committing
  • Not checking after push — run git log or check the remote to confirm your push succeeded
