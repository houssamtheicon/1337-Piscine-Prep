Peer Evaluation Guide

Peer evaluation is a core part of the 42/1337 pedagogy. You evaluate others and are evaluated by others. Understanding the process helps you succeed on both sides.

Overview of the Evaluation System

Each project you submit must be evaluated by at least one peer. The evaluation is a live session where the evaluator reviews your code, runs tests, and asks questions. You receive a grade and written feedback. Similarly, you must evaluate other students' projects to earn evaluation points for your own submissions.

Key point: You cannot pass the Piscine without completing peer evaluations. They are mandatory, not optional.

Preparing for Evaluation

  • Check norminette: Run it before every submission. A norm error means an automatic failure.
  • Check compilation: Your code must compile with gcc -Wall -Wextra -Werror without warnings or errors.
  • Test edge cases: Think about what your evaluator might test and prepare your program for those inputs.
  • Review your code: Be ready to explain every line. Understand why you wrote it that way.
  • Have your Git history clean: Multiple commits with clear messages show good workflow.

What Evaluators Look For

CategoryWhat Is Checked
Norm complianceNo norminette errors in any file
CompilationCompiles with -Wall -Wextra -Werror, no warnings
FunctionalityProgram produces correct output for all test cases
Error handlingProgram handles invalid input gracefully
Code structureWell-organized, logical function separation, meaningful names
UnderstandingYou can explain your code and justify design decisions

How to Evaluate

When you are the evaluator, your role is to be thorough and fair:

  1. Read the subject first — understand what the project requires before looking at the code
  2. Check norminette — run it on every .c and .h file
  3. Compile with flags — use gcc -Wall -Wextra -Werror
  4. Run the program — test with the given examples and your own test cases
  5. Read the code — look for logical errors, hardcoded values, memory leaks
  6. Ask questions — probe the student's understanding of key concepts
  7. Give constructive feedback — explain what they did well and what can be improved

Common Evaluation Questions per Module

ModuleSample Questions
Shell 00/01How do permissions work? What does chmod 755 mean? Explain pipes and redirections.
C 00–04Explain how your ft_atoi works. How does a pointer differ from a variable? What is a null terminator?
C 05–07Explain recursion with your factorial function. How does malloc work? What happens if malloc fails?
C 08–09Why use header guards? How does a Makefile work? What is an object file?
C 10–13How do file descriptors work? Explain function pointers. How does a linked list differ from an array?

Defense Tips

  • Explain your decisions: Say why you chose a particular approach, even if it is not perfect
  • Acknowledge limitations: If you know your code has a flaw, admit it and explain what you would do differently
  • Stay calm: If the evaluator finds a bug, take a breath and explain what might have caused it
  • Do not get defensive: Feedback is meant to help you improve. Listen and ask clarifying questions
  • Show what you learned: Even if the project is incomplete, demonstrating understanding of the concepts counts for something

Professionalism and Communication

Treat every evaluation as a professional interaction. Be on time, be respectful, and be prepared. When evaluating, be honest but kind. When being evaluated, be receptive and engaged. The students you evaluate today may be your evaluators tomorrow.
